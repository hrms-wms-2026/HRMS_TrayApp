# Browser Auto-Connect (Device Pairing) — Design

## Problem

The TrayApp's "Connect OneXso Workspace" screen ([ConnectWorkspaceViewModel.cs](../../../ONEVO.Agent.TrayApp/ViewModels/ConnectWorkspaceViewModel.cs))
requires the user to generate an 8-character activation code on the web portal
(`Settings → Devices`), copy it, switch back to the desktop app, and paste it in.

The "Open Activation Website" button already exists but today just opens the portal's
root URL ([WorkspaceLinks.cs](../../../ONEVO.Agent.TrayApp/Services/WorkspaceLinks.cs)) — it doesn't
do anything with the resulting session. The ask is a second, additive connect path: click
"Open Activation Website" (or a new "Connect via Browser" action), approve in the browser
— auto-skipping login if the browser already has a valid session, exactly like `gh auth
login --web` or Docker Desktop's browser sign-in — and the desktop app finishes connecting
on its own. **The existing paste-code flow (`VerifyAndConnectAsync`, `PasteActivationCodeAsync`)
is not touched.**

## Non-goals

- Changing or removing the manual code entry flow.
- A custom URI protocol callback (`onexso-workspace://`). That extension exists in the
  Windows manifest and a registration script, but nothing parses it today, and it only
  works once a user has re-registered it as Administrator — too fragile for this. Polling
  works identically in dev and prod with no extra install step.
- Listing/revoking devices, admin-initiated pairing — out of scope, same as the existing
  Devices page design.

## Flow

```
TrayApp                    Backend                      Browser (portal)
   |--POST /device/start-->|  create pairing session      |
   |<--request_id,poll_tok-|  (Pending, 5 min TTL)         |
   |--Process.Start------->|-------------------------------|--> /connect-device?request_id=X&device=...
   |                       |                                |   authGuard: not logged in? -> /auth/login?returnUrl=...
   |                       |                                |   -> back here once authenticated
   |                       |                                |   shows "Approve OneXso WorkPulse on <device>?"
   |                       |<--POST /device/approve---------|   user clicks Accept
   |                       |  (TenantPolicy; generates a
   |                       |   code via the same logic
   |                       |   as today's "Generate Code")
   |--POST /device/poll--->|  status=Approved -> returns
   |<--{status:"approved", |   the raw code once, clears it
   |     code}-------------|
   |--(existing) exchange->|  identical to manual entry
   |<--JWT + employee info-|
```

Approve does not invent a new auth/token mechanism — it reuses
`GenerateActivationCodeCommandHandler`'s logic to mint a normal `TrayActivationCode`,
bound to whoever is authenticated in that browser tab. Poll hands the raw code to the
TrayApp, which runs it through the existing `ExchangeActivationCodeAsync` path — the same
code path a manually-typed code takes.

### Security separation

`request_id` travels in the browser URL and is not secret — it only identifies which
pairing session to act on. `poll_token` is generated by the backend at `device/start` and
returned only to the TrayApp over the named pipe; it never appears in the browser or the
URL. Polling requires both `request_id` and `poll_token`, so someone who merely observes
the browser URL (screen share, browser history, shoulder surfing) cannot poll for the
resulting activation code. This mirrors OAuth 2.0 Device Authorization Grant's
`device_code` / `user_code` split (RFC 8628).

## Backend (`HRMS-Backend-v1`)

### New entity: `TrayPairingSession`

System-mode table (not `ITenantOwnedEntity`) — same "System tenant-context" pattern
`ExchangeActivationCodeCommandHandler` already runs under, since `TenantId`/`UserId` are
unknown until approval.

```csharp
public class TrayPairingSession
{
    public Guid Id { get; set; }                  // request_id
    public string PollTokenHash { get; set; }
    public TrayPairingStatus Status { get; set; }  // Pending | Approved | Denied | Expired
    public Guid? TenantId { get; set; }
    public Guid? UserId { get; set; }
    public string? PendingCode { get; set; }        // raw one-time code; set on approve, cleared on first poll pickup
    public string? DeviceName { get; set; }
    public string? DeviceOs { get; set; }
    public DateTimeOffset ExpiresAt { get; set; }    // CreatedAt + 5 minutes
    public DateTimeOffset CreatedAt { get; set; }

    public bool IsValid => Status == TrayPairingStatus.Pending && DateTimeOffset.UtcNow < ExpiresAt;
}
```

Migration adds `tray_pairing_sessions`. No RLS policy needed (system-mode, not tenant-scoped);
follows whatever migration already exists for `AllowSystemModeOnTrayActivationRls`.

### Endpoints — `MonitoringActivationController`

| Route | Auth | Body | Behavior |
|---|---|---|---|
| `POST /activation/device/start` | Anonymous, IP rate-limited (same limiter class as `generate`) | `{device_name, device_os}` | Creates a `Pending` session, 5 min TTL. Returns `{request_id, poll_token, expires_in_seconds}`. `poll_token` is generated raw, only its hash is stored. |
| `POST /activation/device/approve` | `[Authorize(Policy="TenantPolicy")]` | `{request_id}` | Loads session by id; 404 if missing, 410 if expired/already resolved. Resolves `ICurrentUser` (same as `Generate`). Invokes the existing activation-code generation logic to mint a `TrayActivationCode` bound to that user/tenant. Stores the raw code on `PendingCode`, sets `TenantId`/`UserId`, `Status = Approved`. |
| `POST /activation/device/deny` | `[Authorize(Policy="TenantPolicy")]` | `{request_id}` | Sets `Status = Denied` (only if currently Pending and belongs to no other user's approve race — see Error handling). |
| `POST /activation/device/poll` | Anonymous | `{request_id, poll_token}` | Hashes `poll_token`, compares to `PollTokenHash`; 401 on mismatch. Returns `{status: "pending"}` while Pending. On `Approved` with `PendingCode` set: returns `{status: "approved", code}` and clears `PendingCode` (single retrieval — a second poll after pickup returns `{status: "approved"}` with no code, since the code is already consumed downstream by `exchange`). Returns `{status: "denied"}` / `{status: "expired"}` otherwise. |

`GenerateActivationCodeCommandHandler`'s core (rate-limit check, code creation, hashing,
600s expiry) is extracted into a small shared method/internal command both `Generate` and
`Approve` call, so per-user rate limiting (3 codes/hour) applies identically whether the
code came from the Devices page or a browser-approved pairing.

No new endpoint is needed to fetch session details before approval — the frontend gets
`device_name`/`device_os` from the URL query string (cosmetic only; the actual trust
boundary is `request_id` + auth + `poll_token`, not this label).

## Frontend (`Hrms--Web-application`)

New route `connect-device`, added to `app.routes.ts` near the existing `settings/devices`
entry but reachable without a module gate (unlike Devices, this is not employee-initiated,
so no `desktop_agent_gateway` nav entry). `canActivate: [authGuard]` — same guard already
used elsewhere; an unauthenticated visitor is redirected to
`/auth/login?returnUrl=/connect-device?request_id=...&device_name=...&device_os=...`
and returns here once signed in. If the browser already holds a valid session, the guard
passes straight through — this is what gives the "auto-login" behavior the user asked for.

Component `ConnectDeviceApprovalComponent`
(`src/app/modules/settings/feature/connect-device-approval/`):
- Reads `request_id`, `device_name`, `device_os` from the query string. Missing
  `request_id` → error state immediately, no API call.
- Idle state: "Approve OneXso WorkPulse on **{device_name}** ({device_os})?" with
  Accept / Deny buttons.
- Accept → `POST device/approve`. Success → "Connected — you can return to the desktop
  app." Failure (404/410) → "This request has expired. Return to the desktop app and try
  again."
- Deny → `POST device/deny`. Success → "Request denied. You can close this tab."
- No polling on the frontend — the backend call is fire-and-forget from the browser's
  perspective; the TrayApp is the one polling.

`ActivationApiService` gains `approveDevice(requestId)` / `denyDevice(requestId)` methods
alongside the existing `generate()`.

## TrayApp (`HRMS_TrayApp`)

`ConnectWorkspaceViewModel.OpenActivationWebsite` (currently a static `Process.Start` call)
becomes an async `ConnectViaBrowserCommand`:

1. Sends a new IPC message (`IpcMessageTypes.DevicePairingStart`) to `AgentWorker`, mirroring
   `HandleActivationCodeSubmitAsync`. `AgentWorker` calls `_apiClient.StartDevicePairingAsync(deviceName, deviceOs)`
   → backend `device/start` → returns `{request_id, poll_token, expires_in_seconds}`.
2. ViewModel opens the browser via the existing `Process.Start(UseShellExecute=true)`
   pattern at `{WorkspaceLinks.PortalUrl}/connect-device?request_id={id}&device_name={name}&device_os={os}`.
3. `AgentWorker` polls `device/poll` every 2s (client-side backoff not needed at this
   volume) until `approved` (with code), `denied`, `expired`, or its own 5-minute local
   timeout fires first as a safety net.
4. On `approved`, `AgentWorker` runs the code through the same path
   `HandleActivationCodeSubmitAsync` already uses (`_apiClient.ExchangeActivationCodeAsync`
   → `PersistAuth` → `ReplyEnrollmentAsync`), so the TrayApp UI updates via the existing
   `IpcMessageTypes.EnrollmentResult` / `OnStateReceived` path — identical to a manual
   successful connect.
5. On `denied`/`expired`/timeout, replies with a new error code the ViewModel maps to a
   message ("Request denied in the browser." / "The browser request expired — try
   again."), following the same `switch` pattern `VerifyAndConnectAsync` already uses for
   `ErrorMessage`.

New ViewModel state: `IsWaitingForBrowserApproval` (bool) drives a "Waiting for approval in
your browser…" panel with a Cancel button that sends a stop-polling IPC message and resets
state. `VerifyAndConnectAsync`, `PasteActivationCodeAsync`, and `IsValidActivationCode` are
unchanged.

## Error handling

- **Backend unreachable at `device/start`**: ViewModel shows the existing "Can't reach the
  ONEVO backend right now" style message, no browser opens.
- **User closes the browser tab without deciding**: session simply expires after 5 minutes;
  TrayApp's local timeout surfaces "The browser request expired — try again."
- **Two approve calls race** (e.g. double-click): second call sees `Status != Pending`,
  returns 410 idempotently; no double code generation.
- **Rate limit** (3 codes/hour) hit via `approve`: same `429` handling the Devices page
  already has, surfaced as "Too many connection attempts. Try again in a bit."
- **Poll after the code was already picked up** (e.g. duplicate poll from a retry): returns
  `{status:"approved"}` with no `code` — TrayApp treats a second `approved`-without-code
  response as already-handled and stops polling rather than erroring.

## Testing

- **Backend**: unit tests for `Start`/`Approve`/`Deny`/`Poll` handlers (happy path, expiry,
  wrong `poll_token`, double-approve race, rate limit reuse from `Generate`); integration
  test covering the full `start → approve → poll → exchange` chain, alongside the existing
  `TrayActivationIntegrationTests`.
- **Frontend**: `connect-device-approval.component.spec.ts` — missing `request_id`, accept
  happy path, deny happy path, expired/404 on accept; route spec asserting `authGuard` and
  `returnUrl` round-trip.
- **TrayApp**: `ConnectWorkspaceViewModel` tests for the new waiting state, cancel, and each
  terminal poll outcome, following the existing `FakeNamedPipeClient` pattern; `AgentWorker`
  tests for the new IPC handler and its polling loop/timeout, alongside
  `AgentWorkerLifecycleGateTests`/`AgentWorkerCollectionSubmitTests`.
